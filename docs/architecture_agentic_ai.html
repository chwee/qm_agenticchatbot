Q&M Dental Group — AI Enquiry & Enrollment System

How the WhatsApp agents actually work

One WhatsApp conversation carries a participant from "how much is this course" to a paid, receipted enrollment. Underneath it, a CrewAI backend splits the work between four narrow LLM agents and a set of deterministic code paths that never touch a model — including the one path that must never be wrong: money.

01 — Architecture

Request flow, end to end

Every inbound message is one stateless HTTP request — there's no session object. The whatsapp-server gateway forwards it to the backend, a registration gate blocks anyone who hasn't yet given a name/NRIC/email, and the Intent Router decides — mostly without a model — which of the three module agents should handle it.

02 — Design decision

Deterministic and agentic paths call the same code

A slash command and its free-text equivalent are not two implementations that need to be kept in sync — they're two ways of reaching the exact same function. The command handler calls it with regex-parsed arguments; the agent calls it as a tool with LLM-parsed arguments. Neither path is allowed to compute a fee, a schedule, or a payment verdict itself.

03 — Agents

Five agents, four of them narrowly scoped

Every agent is built through the same kickoff_agent() helper in crews/_base.py: a single CrewAI Agent, one Task, run sequentially, delegation disabled, capped at 6 tool-call iterations. What differs per agent is the role, the backstory (hard behavioural rules), and the registered tools.

Utility

Intent Router

Classifies free text into ENQUIRY / ENROLLMENT / PAYMENT

Only runs for free text with no image — /commands are parsed by regex and images are routed to Module C before the router agent is ever invoked. Given the last six turns of chat history, it must also recognise bare confirmations ("intake 2", "yes") as continuing whatever the assistant just offered.

No API key, or the agent errors → falls back to keyword matching (enrol/signup → B, paid/paynow → C, else A).

Module A

Q&M Training Enquiry Assistant

Reactive conversational agent — Proposal §5.3

Answers only from the FAQ knowledge base and its tools — never invents a fee, date, or policy. Resolves references to earlier turns ("what about the fees?") from chat history before calling a tool. Never claims to know the participant's own enrollment or payment status — that always redirects to /mystatus.

Deterministic: /help /courses /fees /schedule /sfc. No key → canned menu reply.

Module B

Q&M Enrollment Pipeline Agent

Extracts course + intake from free text or from a numbered list it showed earlier, and is hard-forbidden from calling Enroll Participant without a specific intake — the auto-pick-next-date default is reserved for the /enroll shortcut, never for a conversation. A course-code-plus-SH-code message short-circuits straight to enrollment, bypassing the LLM entirely, so it can't misread SH2604 as "intake 4".

Deterministic: /enroll /mystatus /invoice via pattern-matched field detection. No key → enrollment cheat-sheet reply.

Module C

Q&M Payment & Accounts Agent

Multimodal verification agent — Proposal §5.5, most autonomous module

This agent only ever sees text — "what do I still owe", "resend my receipt". The moment a screenshot is attached, services/payments.py settles it deterministically before this agent is constructed at all. See the payment-verification flow below.

Settle Payment Resend Receipt Payment Balance Resend Invoice ↔B Enrollment Status ↔B
Deterministic: /receipt, and /pay whenever an image is attached — always, key or not.

Utility

Registration Assistant

Name extraction only, during onboarding

Phone, NRIC and email are always pulled with regex, never by a model. Only when a new participant's free-text reply has leftover, non-boilerplate words after those regexes run is this narrowly-scoped agent asked to isolate a full name from the sentence — or reply NONE. It cannot see or influence the other three fields.

No API key, or leftover text is empty → registration just asks again in plain English.

04 — The money path

Payment verification never asks an LLM for permission

An invoice can need one proof or two — a SkillsFuture claim covering the subsidy, a PayNow transfer covering the net payable, or both, arriving as separate images since WhatsApp only ever delivers one image per message. Each screenshot is graded independently against whatever balance is still outstanding for its type.

05 — Tools

14 tools, thin wrappers over one service layer

Every tool reads the sender's whatsapp_id, phone, and any screenshot from request-scoped context — never from an argument the LLM fills in — so a hallucinated or injected argument can change a decision at worst, never let an agent act as a different participant or pull binary image data into the token stream.

06 — Why this shape

What the split actually buys

01

The must-not-fail paths are code-guaranteed

Every slash command and the entire payment-settlement flow run without a model in the loop. Reliability, latency, and cost for "did the money get recorded correctly" come from code review, not prompt engineering.

02

The system degrades, it doesn't fall over

With OPENAI_API_KEY unset, every deterministic command still works and free text falls back to keyword routing. Agentic reasoning is a value-add layer on top of a working system, not a dependency the whole product needs to stay up.

03

Agentic and deterministic answers can't diverge

Both paths call the same services/*.py functions. An agent's job is to figure out what the participant wants — it never computes a fee, a schedule, or a payment verdict itself, so the two paths are structurally unable to disagree.

04

Shared tools save a hand-off protocol

Module B borrowing Module A's course lookups, and Module C borrowing Module B's invoice lookups, let one agent resolve a cross-cutting question in a single turn instead of needing an inter-agent messaging layer.

05

Identity can't be prompted away

Tools read whatsapp_id, phone, and screenshots from per-request context, never from LLM-filled arguments. A prompt injection can steer a decision at worst — it can't make the agent act as a different participant.

06

Stateless by design, for free concurrency

Every turn re-queries the database and re-derives numbered lists from chat history instead of holding session state. Multi-user isolation falls out of partitioning by whatsapp_id, with nothing to leak between concurrent requests.
