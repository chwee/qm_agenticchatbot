For stakeholders — process, data & automation value

What happens at each step, and what it replaces

Every box in the diagram above is broken down below into what a business reader needs: the activity being performed, the data it needs coming in, the data it produces going out, and — since this whole journey is carried out by Agent A — what running it as an autonomous agent buys the business over a person doing the same steps by hand.

A

Agent A — the Enquiry & Lead Nurturing Agent

Persona: "Q&M Training Enquiry Assistant". Answers only from the official course knowledge base and live database — never invents a fee, date, or code. Owns steps 8–12 below; captures lead details and escalates to a human staff member whenever it isn't confident, instead of guessing.

For engineers — implementation trace

Same journey, at file-and-function level

The rest of this page repeats the identical path with exact code references, for anyone implementing or auditing it.

Stage 1 — Inbound: phone to backendGetting the message onto the orchestrator

01

Customer sends a WhatsApp message gateway

Either a slash command (/schedule C2601) or free text ("What courses do you offer, and when's the next intake?"). Both are handled by the same pipeline — the fork happens twice downstream, not here.

02

whatsapp-server receives the message event gateway

whatsapp-server/server.js — the only component with a live WhatsApp Web session. On a message event it downloads any attached media (none, for an enquiry) and forwards a JSON payload.

03

POST /webhook/whatsapp gateway backend

The gateway's only outbound call for inbound traffic. Received by FastAPI on backend :8000, defined in app/main.py.

04

orchestrator.handle_inbound(payload) backend

app/orchestrator.py — the single entry point for every inbound message. Parses the sender (whatsapp_id, phone, display name) from the gateway's from field.

05

Customer isolation database

repo.get_or_create_customer(whatsapp_id) — an atomic upsert against the customers table. This is the partition key for every other lookup; no two users ever share state.

06

Registration gate decision

Checks phone_confirmed, full_name, nric, email are all on file. For this instance the customer is assumed already registered, so the turn proceeds to routing — an unregistered customer would branch into the free-text registration flow instead, covered in Instance 02 — New Customer Registration.

07

context.set_message(...) backend

app/context.py — a request-scoped ContextVar holding whatsapp_id, phone, and the full customer row, so tools never receive identity fields as LLM-fillable arguments.

Stage 2 — Fork 1: intent routing/command vs. free text

08

router.route(payload) decision

app/crews/router.py — parse_command(body) checks whether the message starts with /.

09a

Branch — slash command backend

If it matches an entry in the COMMANDS registry (app/commands.py), parse_command returns a fully-structured routing decision — {module: "A", command: "schedule", arg: "C2601", is_command: true} — deterministically. No LLM is ever consulted for a well-formed command.

09b

Branch — free text backend

classify_free_text(body, has_media=False) first reads the last 6 turns via repo.recent_memory(wid, limit=6) database (chat_memory table) for context.

09c

Router Agent LLM classification OpenAI

If OPENAI_API_KEY is set, kickoff_agent(role="WhatsApp Intent Router") calls GPT-4o-mini with the conversation history and the COMMAND_REFERENCE block, and returns one label: ENQUIRY, ENROLLMENT, or PAYMENT. Without a key (or on agent failure), _heuristic() keyword-matches instead — the system degrades gracefully rather than failing the turn.

10

Both branches converge backend

Either path produces the same shape: a routing decision with module: "A". The orchestrator logs the routing line and dispatches to module_a.run(payload, decision).

Stage 3 — Fork 2: Module A reply strategyDeterministic command vs. CrewAI agent

11

route.is_command? decision

app/crews/module_a.py: run() — the second and final fork for this instance.

12a

Deterministic reply backend

_command_reply("schedule", "C2601") calls straight into services/courses.py: format_schedule() (or format_courses() for a bare /courses). No agent, no LLM token spent — same code path a human-typed exact command always takes.

12b

Agentic reply backend

_run_agent(body) reads 8 turns of history database (chat_memory), then kickoff_agent() builds a CrewAI Agent + Task + single-agent Crew — role "Q&M Training Enquiry Assistant", backstory = the full FAQ knowledge base, tools = MODULE_A_TOOLS (List Courses, Course Fees, Course Schedule, SkillsFuture Info, Save Lead Data, Flag For Staff Review).

13

LLM reasons and picks a tool OpenAI

GPT-4o-mini reads the task description (conversation history + new message) and decides which tool(s) answer it — here, List Courses and/or Course Schedule. Per the module's persona, it must resolve "which course" from chat history before guessing, and never invent a fee, date, or code.

14

Tool executes backend

tools/course_tools.py: course_schedule_tool() reads context.customer(), then calls the exact same services/courses.py: format_schedule() the deterministic path uses — one source of truth for both paths.

15

Database read (both paths converge here) database

repositories.py — resolve_course_arg() → get_course_by_name() / get_course_by_course_id(), then get_schedules(course_id). Raw SQL SELECT against the courses and course_schedules tables, e.g.: SELECT * FROM course_schedules WHERE course_id = %s AND active = TRUE ORDER BY start_date. Rows come back with each intake's schedule_id (SH-code), label, and seats.

16

Formatting backend

format_schedule() renders the rows into WhatsApp-ready text: course name, C-code, then each intake as [SH-code] label (seats left).

17

Reply shaping differs by branch OpenAI backend

Command path: the formatted text is the reply, verbatim. Agent path: the formatted text comes back to the LLM as a tool Observation; the agent then writes a short, natural sentence around the facts — carrying every code/date/fee over exactly, but composing the surrounding language itself rather than pasting the raw list.

Stage 4 — Outbound: backend to phonePersisting and delivering the reply

18

Chat memory persisted database

Back in orchestrator.handle_inbound(): repo.add_memory(wid, "user", body) and repo.add_memory(wid, "assistant", reply) — two INSERTs into chat_memory, best-effort (a write failure here never blocks the reply).

19

Trace logged backend

query_log.emit() mirrors the full TURN → ROUTING → REPLY trace (plus every tool call and its result) to console and, if QUERY_LOG_ENABLED=true, to backend/logs/query_log_YYYY-MM-DD.txt.

20

Delivery gateway

whatsapp_client.send_whatsapp(routing_id, reply) sends POST /send-reply to whatsapp-server (WHATSAPP_SEND_URL), which pushes the text back through the linked WhatsApp Web session to the customer's phone — the same chat the enquiry came from.

Why two forks matter: the deterministic command path and the CrewAI agent path are genuinely two different code routes through Module A, but they are designed to never disagree — both terminate in the exact same services/courses.py functions and the exact same SQL in repositories.py. The agent only changes how the answer is phrased, never what facts it's allowed to state.
