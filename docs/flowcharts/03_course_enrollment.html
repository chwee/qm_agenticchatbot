What "successful" actually means here

A successful enrollment is not just a database row. By the time the customer sees a confirmation, the system has already: reserved their seat on that specific intake, generated a legally-usable invoice PDF with an embedded PayNow QR code, emailed it to their registered address, and opened a payment record waiting for Module C to update the moment proof of payment arrives. All of that happens inside one WhatsApp turn — the same guarantees whether the request came from a typed shortcut or a casual sentence. If the customer later needs to back out, see Instance 04 — Course Cancellation & Credit Note for how every one of these effects gets reversed.

Stage 2 — Resolving course, intake & profileDeterministic match, quick shortcut, or Agent B

02

route.is_command, or _quick_enroll_from_text(body) decision

module_b.py — an /enroll command, or free text where both a C-code and an SH-code regex-match (_C_CODE_IN_TEXT / _SH_CODE_IN_TEXT), short-circuit straight to _smart_enroll() — no LLM call.

03

_smart_enroll(params, customer) backend

Re-classifies every pipe-separated field by pattern regardless of position: valid_nric(), valid_email(), an SH-code regex, then a trailing bare integer as schedule_no. The first remaining text resolves to a course via courses_svc.resolve_course_arg(); a second becomes a name override. Blank name/NRIC/email fall back to customer.

04

_run_agent(body) OpenAI

kickoff_agent(role="Q&M Enrollment Pipeline Agent", tools=MODULE_B_TOOLS). Backstory hard-requires a specific, participant-named intake before ever calling Enroll Participant; instructed to resolve a bare confirmation ("intake 2") against its own previous numbered reply in chat history rather than re-querying Course Schedule.

05

Validate Enrollment / Enroll Participant tools backend

tools/enrollment_tools.py — both wrap the exact same services/enrollment.py functions the command path calls via _smart_enroll(). One pipeline, two entry points.

Stage 3 — The enrollment pipelineservices/enrollment.py: enroll()

06

validate_enrollment() + schedule resolution decision

Checks course/name/NRIC/email are non-empty, the course resolves via repo.get_course_by_name(), and NRIC/email pass format checks. Immediately after (folded into the same diagram gate): an SH-code must belong to the resolved course, and a schedule_no must be in range — either failure returns a specific error with the available intakes listed.

07

repo.active_enrollment_for_course(...) database

The duplicate guard. A match short-circuits with the existing enrollment's status and a next-step hint (pay / resend invoice / resend receipt) instead of creating a second record.

08

compute_fee() + new_invoice_no() backend

compute_fee(full_fee, sf_subsidy_cap) → (fee, subsidy, net); new_invoice_no() mints the invoice number.

09

repo.create_enrollment(status="enrolled") database

Followed by repo.adjust_schedule_seats(schedule_id, +1), repo.set_customer_status(whatsapp_id, "enrolled"), and (legacy) repo.set_lead_status() if a lead row exists for this phone.

10

generate_invoice_pdf(enrollment) backend

app/pdf.py — ReportLab, embeds a PayNow QR encoding the company UEN and the invoice number as payment reference.

11

_send_invoice_email() → email_service.send_email() backend

SMTP delivery with the PDF attached; body includes SkillsFuture claim instructions. Logged to console instead of sent when EMAIL_ENABLED=false.

12

repo.update_enrollment(status="invoice_sent") + repo.record_payment(verdict="pending") database

Opens the payments-ledger row Module C will update in place, rather than insert a new one, once payment proof is verified.

13

Course, date, name, NRIC, a fee line adjusted for SkillsFuture wording (never upgraded to "fully claimable" unless net payable is genuinely S$0), the invoice number, and the /pay next step.
