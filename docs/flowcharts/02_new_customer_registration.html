What happens at each step, and what it replaces

A stakeholder view of the same journey: what happens, what information it needs, what it produces, and what running it automatically buys the business over a person manually processing sign-up forms.

G

The Registration Gate — not an AI agent

A deterministic checkpoint every customer passes through exactly once. It reads structured data with strict rules, not judgement — the one narrow exception is a single-purpose AI call used only to guess a person's name from casual phrasing, never phone, NRIC, or email.

Same journey, at file-and-function level

The same path with exact code references, for anyone implementing or auditing it. Covers the branch where the customer is not yet fully registered — an already-registered customer's message skips straight past this gate to router.route() (see Instance 01).

Stage 1 — Arrival & lookupGetting the message to the registration gate

01

Message received & forwarded gateway

whatsapp-server forwards the raw message via POST /webhook/whatsapp, same as every other inbound message.

02

orchestrator.handle_inbound(payload) backend

app/orchestrator.py — parses the sender, then repo.get_or_create_customer(whatsapp_id) atomically upserts a record. For a @c.us account whose phone the gateway already supplied, repo.set_customer_phone() auto-confirms it here if not already confirmed.

03

_is_registered(customer)? decision

True only when phone_confirmed, full_name, nric and email are all set. This diagram covers the False branch; True skips straight to router.route() (Instance 01).

Stage 2 — Extracting whatever this message contains_advance_registration() and its two extraction paths

04

_advance_registration(whatsapp_id, body, customer) backend

Entry point for the whole gate; calls _extract_registration_fields(body, customer).

05

_parse_piped_reply(body, customer) decision

Checks for the exact shortcut: 4 pipe-separated parts (phone|name|NRIC|email), or 3 parts (name|NRIC|email) if phone is already confirmed. Validates the phone digit-count and that the email contains "@" before accepting. On a match, returns immediately — free-text parsing never runs.

06

_parse_free_text_reply(body) backend

On no shortcut match: _EMAIL_RE, then _NRIC_RE, then _PHONE_TOKEN_RE each find and strip their match from the remaining text in turn. _is_valid_phone() rejects 15-digit WhatsApp LIDs so one is never mistaken for a phone number.

07

Name resolution OpenAI (fallback only)

Whatever's left after stripping known tokens and filler words (_NAME_FILLER_RE) goes through _clean_name_remainder() — must look like a real name (starts with a letter, 1–5 words, ≤60 chars). Only if that fails, OPENAI_API_KEY is set, and non-filler text remains does _llm_extract_name() run: a CrewAI agent scoped to name-extraction only, explicitly told to ignore phone/NRIC/email.

Stage 3 — Saving progress & the two guard checksPersisting fields, catching duplicates, checking completeness

08

repo.set_customer_phone(whatsapp_id, phone) database

Saved first, and only if newly found and not already confirmed. Raises ValueError if that phone already belongs to a different whatsapp_id → status = "phone_collision", and the turn ends here with the recheck reply.

09

repo.update_customer(whatsapp_id, **updates) database

Any newly found full_name/nric/email not already on file is saved. A field already set from an earlier message is never overwritten.

10

_missing_fields(customer) decision

Recomputed against the just-updated record: phone_confirmed, full_name, nric, email.

11a

Incomplete → _registration_prompt(missing, has_progress) backend

First-contact wording ("Welcome to Q&M Dental Training! 👋…") if nothing was known before this message; "Thanks! I still need…" if some fields were already on file. Reply is returned and the turn ends — the customer's next message re-enters this flow at step 02.

11b

Complete → repo.register_customer(...) backend

Commits the finalized record. Can still raise ValueError here (a last-moment collision) → phone_collision. Otherwise status = "complete" and the reply is _REG_CONFIRM — a welcome message inviting the customer to ask about courses, fees, SkillsFuture, or enrol.

Stage 4 — OutboundDelivering the reply

12

whatsapp_client.send_whatsapp(routing_id, reply) gateway

Same delivery path as every other reply: POST /send-reply to whatsapp-server, back to the same WhatsApp chat. Note: unlike a normal enquiry turn, context.set_message() and router.route() are never reached while registration is incomplete — chat memory for this turn is still recorded, but no module (A/B/C) runs.

Why the AI boundary matters: every identifier that could cause real harm if guessed wrong — a phone number, an NRIC, an email address — is only ever accepted from an exact pattern match or an exact shortcut. The single point where AI is allowed to infer something is a person's name, the one field where a wrong guess costs nothing worse than the bot asking again. That boundary is enforced in code (_llm_extract_name() is never given the option to return a phone, NRIC, or email), not just by convention.
