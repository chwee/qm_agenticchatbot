Course Cancellation & Credit Note

Traces what happens when an already-enrolled customer's course is cancelled. Unlike Instances 01–03, this process has no WhatsApp path and no AI agent — it is entered and driven entirely by staff through the accountant Admin Portal. It's included here in the same format because it's the process that actually reverses what Instance 03 — Course Enrollment created: it un-reserves the seat, cancels the enrollment, and issues the customer's refund document.

No gateway/WhatsApp and no OpenAI swatches this time — neither appears anywhere in this process. See the callout below.

Two things worth knowing before this looks like a "cancel → approve" workflow

  • The cancellation already happened by the time anyone "approves" anything. Requesting a credit note immediately sets the enrollment to cancelled and frees the seat. The later "approve" step doesn't decide whether to cancel — that's done — it only finalizes the credit note record, generates the PDF, and tells the customer.
  • There's no way to reject a request. The database schema has a 'rejected' status ready for it, but no code path ever sets it — once a cancellation is requested, the only next step wired up is approval.

For stakeholders — process, data & automation value

What happens at each step, and what it replaces

A stakeholder view of the same journey. Because this process has no AI step, "automation value" here means something more modest than in Instances 01–03: consistency, an audit trail, and one submission replacing several manual ones — not judgement replacing a person.

S

Process owner: Staff, via the Admin Portal — not an agent

There is no Agent A/B/C equivalent here. A human decides to cancel and a human approves the credit note; the system's job is to make both actions safe, consistent, and fully recorded — not to decide anything on its own.

For engineers — implementation trace

Same journey, at file-and-function level

Exact code references for anyone implementing or auditing this process.

Stage 1 — Request (staff-initiated, immediate effect)app/admin.py → services/payments.py: request_credit_note()

01

Admin Portal authentication staff

app/admin.py — HTTPBasic, hardcoded ADMIN_USER/ADMIN_PASS checked via secrets.compare_digest(). Explicitly marked in the code as POC-grade — override via env vars for a real deployment.

02

POST /admin/credit-notes/request staff

Params enrollment_id: int, reason: str = "Cancellation" → payment_service.request_credit_note(enrollment_id, reason).

03

Guard: already cancelled? decision

services/payments.py — repo.get_enrollment(enrollment_id); returns {"ok": False} if not found or if enrollment["status"] == "cancelled". This is the only eligibility check — there is no "must be unpaid" or similar restriction.

04

Create + cancel, synchronously database

repo.confirmed_payments_for_enrollment() sums detected_amount for verdict='confirmed' rows → total_paid. new_credit_note_no() (utils.py, "CN" prefix, credit_note_seq) then repo.create_credit_note(...) INSERTs into credit_notes (status defaults 'requested'), repo.update_enrollment(status="cancelled"), and repo.adjust_schedule_seats(schedule_id, -1) (clamped ≥0 via GREATEST(seats_taken + delta, 0)) — all three writes happen in this one call, before any approval.

05

send_email(settings.accounts_email, ...) backend

Internal notification only — enrollment["email"] (the customer) is never touched at this stage.

Stage 2 — Approval (separate staff action, no status guard)app/admin.py → services/payments.py: approve_credit_note()

06

POST /admin/credit-notes/{id}/approve staff

→ payment_service.approve_credit_note(credit_note_id). An identical route also exists in app/dbadmin.py (database manager UI), calling the same function.

07

repo.approve_credit_note(credit_note_id) database

UPDATE credit_notes SET status = 'approved', resolved_at = now() WHERE id = %s. No check that the row is still 'requested' — calling this twice is harmless but not prevented.

08

generate_credit_note_pdf(enrollment, cn) backend

app/pdf.py — writes generated_dir/credit_note_{cn_no}.pdf with "Credit Amount" (cn.amount, falling back to enrollment.net_payable) and "Reason".

09

send_email(enrollment["email"], ..., attachments=[pdf_path]) backend

The customer's only notification in the entire flow — sent only here, only on approval.

Known gap: db/schema.sql's credit_notes.status CHECK constraint allows 'requested' | 'approved' | 'rejected', but no reject_credit_note() function exists in repositories.py or services/payments.py, and no route in admin.py exposes one. A request that shouldn't be honored currently has no built-in way to be declined — staff would have to handle that outside the system.
