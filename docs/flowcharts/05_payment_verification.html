Payment Verification

Picks up right where Instance 03 — Course Enrollment left off: an invoice has already been generated and emailed, and a pending payment record is waiting. Traces what happens when the customer submits proof of payment. This is the most agentic instance in the series: a vision model actually looks at the screenshot and extracts what it sees — but deliberately never decides the outcome itself. A separate, fixed set of business rules checks the AI's reading against the real invoice balance before anything is confirmed, receipted, or flagged. That boundary is the whole story of this diagram.

The boundary that makes this safe to automate

The vision model's only job is perception: read the screenshot, report what it sees, say how confident it is. It never says "yes, accept this." Whether a screenshot actually counts as payment — checked against the real outstanding balance, the tolerance for rounding, and a confidence threshold — is decided entirely by ordinary code (_evaluate_proof()), the same function every single time, with no model in that decision. If the AI is ever swapped for a different vision model, this rule never has to change; if the business rule ever changes, no prompt has to change.

Agent C — Payment Verification & Accounts

Two distinct AI roles hide under one name. When a screenshot is attached, a GPT-4o vision call reads it — always triggered directly by code, never by an agent's own choice, so the money path never depends on conversational judgement. When there's no image, a separate conversational agent ("Q&M Payment & Accounts Agent") handles the chat, but only by calling tools for real figures — it never states a balance or invoice number from memory.

Stage 1 — Arrival & the key forkmodule_c.py: run()

01

Gateway → Orchestrator → Router gateway

Same as Instance 01, dispatching to module_c.run(payload, route) once intent = PAYMENT (or any message with an attached image, which the router treats as payment intent regardless of text).

02

if data: return payments.process_payment(...) decision

In module_c.py: run() — data, mimetype = context.media(). This plain if is the entire "which path" decision; there is no LLM call before it. Only when data is empty does the function fall through to the conversational agent.

Stage 1b — No image: the conversational agent's tool-use loopmodule_c.py: _run_agent()

03a

Read the request OpenAI

_run_agent(body) pulls repo.recent_memory(wid, limit=8) and folds it into the task prompt alongside the new message — so "did my payment go through?" right after an earlier invoice mention still resolves correctly.

03b

Reason about intent OpenAI

kickoff_agent(role="Q&M Payment & Accounts Agent", tools=MODULE_C_TOOLS) — GPT-4o-mini classifies the request against the backstory's explicit playbook: receipt request → resend it; "how much do I owe" → check balance, don't guess; invoice number missing → look it up rather than ask the customer to.

03c

Pick the matching tool OpenAI

One of MODULE_C_TOOLS: Payment Balance (outstanding_balance_text()), Resend Receipt (resend_receipt()), Resend Invoice (resend_invoice(), shared with Module B), or Enrollment Status (status_text(), shared with Module B). Settle Payment is technically in the list too, but with no image in context it would just report "No screenshot received" — the agent's own instructions steer it away from calling that tool here.

03d

Tool executes against the real record backend

Every one of these tools reads whatsapp_id/phone from context (never an LLM-supplied argument) and queries the exact same payments/enrollments tables the vision path writes to — there are not two sources of truth for what's owed.

03e

Compose the reply OpenAI

The backstory is explicit: any amount, invoice number, or code a tool returns "must be carried over exactly — never round, reword, or guess one." The LLM's only remaining job is natural phrasing around those facts.

Stage 2 — Resolving the invoiceservices/payments.py: process_payment() (part 1)

03

Invoice number resolution backend

Priority order: the /pay command's argument; else _INVOICE_RE matched against the free-text caption (e.g. "pay for INV-2026-0861"); else, inside process_payment(), repo.latest_enrollment(whatsapp_id) — but only used automatically if that enrollment's status is invoice_sent or awaiting_payment.

04

Validity checks decision

repo.get_enrollment_by_invoice() not found; whatsapp_id/phone mismatch; or status in ("paid","receipt_issued") — each returns its own specific reply and stops here.

05

_remaining_balances(enrollment, confirmed) backend

Sums confirmed proofs by payment_type so far, subtracts from sf_subsidy and net_payable respectively — the per-type outstanding amounts the vision step's result will be checked against.

Stage 3 — Vision extraction and the evaluation boundaryservices/payments.py: extract_payment_proof() + _evaluate_proof()

06

extract_payment_proof(image_b64, mimetype) OpenAI

Calls settings.openai_vision_model (GPT-4o) with temperature=0 and a strict-JSON prompt (_VISION_PROMPT) asking for is_payment_proof, readable, payment_type, detected_amount, reference, confidence, explicitly instructed to use null rather than invent a value. Returns raw facts only — no verdict.

07

_evaluate_proof(extracted, remaining) decision

Pure business logic, zero model calls: unreadable if not readable/not a recognised proof/no amount; mismatch if the type isn't one of the two known types, the relevant balance is already ≤0, the amount exceeds balance + _TOLERANCE (0.01), or confidence < settings.auto_confirm_threshold; otherwise confirmed.

08

Record the attempt database

repo.pending_payment_for_enrollment() — if the invoice's placeholder row (from enrollment) is still pending, repo.update_payment() resolves it in place for the first proof; every subsequent proof (a second type, or a retry) calls repo.record_payment(), inserting a new row — preserving full attempt history either way.

Stage 4 — Acting on the verdict_confirm_proof() / _flag_mismatch() / inline unreadable reply

09

confirmed → _confirm_proof(enrollment, payment) backend

new_receipt_no(); generate_receipt_pdf(); send_email() with the PDF attached. Then sums all confirmed proofs — if the total now covers enrollment["fee"] within tolerance, repo.update_enrollment(status="receipt_issued"); otherwise the reply itemises exactly what's still needed (SkillsFuture and/or PayNow) via _remaining_balances() again.

10

mismatch → _flag_mismatch(enrollment, payment) backend

repo.add_staff_task(reason="payment_mismatch", module="C", payload=raw_extract); send_email(settings.staff_email, ...) with the full detected detail. The customer's reply never states a rejection — only that it's under review.

11

unreadable → inline reply backend

No staff task, no email — just a request to resend a clearer screenshot. The attempt is still recorded (step 08) so a pattern of repeated unreadable submissions is visible in the data.
