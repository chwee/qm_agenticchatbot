- **Task 44** — `router.py`: the two separate reminder-continuation overrides (`_last_assistant_offered_reminder`, scanning only the assistant's recent turns; and a standalone `_has_reminder_intent` check on the participant's new message) consolidated into one `_reminder_in_progress()`, delegating to Module A's own `_recent_reminder_intent()` — neither of the two original checks alone could see a bare email-only reply continuing a participant-initiated request from a turn or two back, since "remind" appeared only in the participant's OWN earlier message, which neither check scanned.
- **Requirements Traceability table**: Requirement 4's row gains Task 44 (AC15).

### v1.24 — 2026-08-23 (decision recorded, no code change)

## Implementation Overview

This plan breaks `design_qm.md`'s ten components into ordered, checkable implementation tasks that satisfy the eleven requirements in `requirement_qm.md`. The build order follows the design's own layering: schema and configuration first, then the shared services/repository layer (so no module ever duplicates a business rule), then the deterministic command surface, then each module's agentic layer on top of it, then the operational surfaces (admin, scheduling), and finally the hardening/testing work the design document explicitly flagged as outstanding.

Tasks for Phases 1–8 describe the system as it exists in this repository today — each is checked off with the file(s) that implement it, so this plan doubles as a build-verification record. Phases 9–10 are **not** yet complete: they are the gaps `design_qm.md`'s Security, Testing Strategy, and Deployment sections called out (no unit test suite, shared admin credential, no rate limiting, plaintext PII, no automated backups). Those are left unchecked as the actionable backlog. Tasks 6, 9.3, 10.3, and 14.1 (progressive registration, v1.1) were reopened and have since been reimplemented and verified end-to-end — see Version History above. Task 10.4 (Module B enrollment confirmation step, v1.2) is implemented and checked off, with one explicitly-accepted partial-reliability gap documented in its own entry — not a blank spot in the plan, a known and reported limitation. Tasks 7, 7.1, 9.2, 10.2, and 11.2 (slash commands removed, v1.3) are implemented, tested end-to-end, and checked off — `commands.py` deleted, every module's deterministic command branch removed, and every affected user-facing string rewritten to natural language.

### Implementation Strategy
- Build bottom-up through the layers in `design_qm.md`: `db/schema.sql` → `repositories.py` → `services/*.py` → `tools/*.py` → `crews/*.py` → `orchestrator.py`, so every higher layer has a stable, tested layer beneath it.
- ~~Stand up the deterministic path for each module before its agentic path~~ — retired as of v1.3 (Requirement 7): there is no deterministic command path left to build first. Every module's free-text agent (or canned fallback) is now the only path, alongside the two explicitly-preserved exceptions: the image-triggered money path (Module C) and the C-code+SH-code quick-enrol shortcut (Module B).
- Keep `services/*.py` as the only place a business rule is written; every task that adds a tool must call an existing or newly-added service function, never re-implement the rule at the call site (design_qm.md, Design Patterns Applied — Facade).

### Development Approach
- **Testing Strategy**: fixture-based tests against `POST /webhook/whatsapp/sync` (with `WHATSAPP_ENABLED=false`) for the money path (still fully non-agentic, unaffected by v1.3) and the C-code+SH-code quick-enrol shortcut; Ragas-based scenario evals (`backend/evals/`) for the conversational agents' free-text reasoning, which is now the primary interaction surface for everything else. The two suites still don't overlap, but the balance has shifted — most of the system's behaviour now depends on agent quality, not deterministic code.
- **Integration Strategy**: the gateway and backend integrate purely through the `POST /webhook/whatsapp` / `POST /send-reply` HTTP contract (Component 1 ↔ Component 2 in `design_qm.md`); every other component integrates in-process through direct Python calls, with `repositories.py` as the single database integration point.
- **Deployment Strategy**: three independently-started local processes today (Docker Compose for Postgres only; `uvicorn` and `npm start` run bare). Phase 10 tracks the containerisation and Cloud-API-swap work needed before a production rollout.
